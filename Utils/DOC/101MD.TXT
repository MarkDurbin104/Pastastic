1.0	Keyboard Scan Codes
	The leyboard assigns unique codes known as scan codes to each keypress, it then notifies the processor (via int 09h) that a key has been pressed or released.  When the processor executes int 09h, the device driver reads the key's scan code, checking first for toggle keys such as Shift and Num Lock.

	1.1  Toggle Status Byte
	If a toggle key has been pressed or released the BIOS status byte is updated.

	1.2  Special Key Combinations
	Next the device driver checks for special key combinations (such as Ctrl-Alt-Del) and, if necessary, executes their special handlers.

2.0	Scan Code Conversion
	If the previous process has not "weeded out" the scan code as a special key combination or toggle key, the device driver transaltes it to it's ASCII equiva-ent.  If no ASCII value exists for that scan code the ASCII is set to sero.

	2.1  Scan Code To Keyboard Buffer
	The ASCII value and the original scan code are then passed to PC-MOS for placing in the keyboard buffer.
	2.2  Double Zero
	The  00  key is a special case and is passed to PC-MOS as two 0's.

3.0	Reading The Keyboard Buffer

	3.1  Buffer Size
	The keyboard buffer has room for 15 keys with their scan codes.  If there are more that 15 keys entered they will be ignored and beep will sound.
	3.2  Access
	Once the keypresses are in the keyboard biffer they are available to teh application layer via the normal routes i.e. getch(), ki() etc.

4.0	Magnetic Card Reading Operation
	4.1  Place MCR in Read Mode
	When the application requires that a magnetic card is read, it passes a command via OI_CTRL to the device driver.  The keyboard is then placed in a mode for reading this information.
	The MCR will then be enabled and when the card is read, all three tracks of information will be passed into the keyboard's internal buffer.
	4.2  Read Track Information
	The application must then ask for track information, again via IO_CTRL.  The reason for separating the request for read and the track information is that the device driver has no way of knowing which of the three tracks is required.  If on the other hand the track number was passed with the first request there would be no means of reading another track.
	4.3  Data Conversion
	Once the information for the track required has been input from teh keyboard/MCR, it will be converted by the device driver into a readable ASCII format and then passed back to the application.
	4.4  Read Abort
	If a key is pressed before the card is read, the read operation is cancelled and the key placed in the keyboard buffer.

5.0	Keyboard Buzzer Control
	If the application needs to sound the keyboard buzzer (Card Read OK etc.) it may do so via the IO_CTRL function.  The function will sound the buzzer for 250ms.
