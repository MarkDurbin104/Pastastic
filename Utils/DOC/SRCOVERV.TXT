INTRODUCTION 
This introduction has been divided into two parts, the first explaining some background information about GPA and the second describing this document. 
Why GPA (WHY NOT C.O.T.S.) ? 
GPA was designed to meet two needs. The first was to supply a postal point of sale program with specific functionality to the Polish post office (running in Polish).  This program had a logical specification and was due for delivery in ten weeks, unfortunately the physical design & coding had not been initiated and the software it was to be based on was not capable of the required functionality.
As Unisys were following leads of the same nature as the Polish system in many other countries, the second need was to avoid this position in the future,  by providing a software platform for postal point of sale that could be easily configured for language/location, hardware, operating system, database and peripherals,  therefore the name - Generic 
Postal Architecture.  
At the time (and possibly still today) there was not a COTS software package that met with the above criteria. 
About this document 
The intention of this document is to describe the underlying source code and data structures that form GPA, the concepts behind them and reasons for any deviation from the original design.  So that anyone wishing to maintain GPA should be able to ascertain sufficient information to point them in the right direction.  GPA is divided, as many 4GE s are, into a development and runtime systems. The development system s outputs are interpreted by the runtime system.  
As the main emphasis of the document is maintenance, the focus must be upon the runtime system as this is where any problems (from the user's point of view) will appear.  However the interfaces between the development and runtime systems are covered in detail. Aspects of the development system are mentioned where it aids clarity.  
This document should be read in conjunction with the following documents:    
MAIN LOGICAL COMPONENTS 
Form 
A form is any screen display or printed report.  There are several types of Form, each is broken down into multiple form-fields, each form-field having a behavioral classification, format and attributes describing style, 
positioning and optional associated datastore reference, variable and action. 
Datastore 
A datastore is a representation of a table in the physical database. Consisting of the structure of the records  i.e. the order, format, type and length of the data elements within the record, and the primary and secondary indexes onto that table.  The data types referred to within a datastore definition are mapped at runtime into the physical data types available from the database. 
Action 
An action is a 4GL macro or function defined in a textual form and then tokenized into reverse polish notation for easy and fast interpretation by the runtime system.  This gives the control of an interpreted language without most of the speed penalties. An action can however consist of a single Form or actions may be written in a 3GL and compiled/linked with the runtime system for speed critical or other special requirements. 
Device 
A device is a code module containing all the references to, and data regarding, one particular system dependent element or type of element within the physical the runtime system. This can be any part of the runtime environment that can be logically separated from the other parts i.e. the database access, the screen access, a particular peripheral or some operating system dependent sections of code. The intention is that any physical part of the system that may change between implementations is placed in a device. 
Localization 
Localization falls in to two main categories the country/location and the language/dialect spoken. The former is unlikely to change within an implementation but there may be a requirement for multiple languages within one local. e.g. Wales or India. The country information consists of  general configuration information including date type ( GREGORIAN / JULIAN / ARABIC / PERSIAN or CHINESE),  time/money/weight formats and the specification of up to ten language sections. The language sections contain font, keyboard logical/physical mapping, all textual information, including the names of months/days etc. and system error messages. The font contains a picture of each character, the left/right anchoring (or up/down for Chinese etc.) any diacritic marks (spacing or non-spacing) and the contextual analysis information for script languages such as Persian, Hebrew and Arabic.  The language section should contain all the  strings  used within the 4GL (CAPTURE has the text strings hard coded into the 4GL but as it is unlikely to be run in any other language so this is not necessarily a problem).

Once the configuration and language information has been loaded, the Forms, Actions and Datastores are loaded. The first form (named  logon ) is then processed. All processes communicate with each other via the standard passed/returned values in function calls and via global variables. 
The devices, however, may only be accessed via the message process.  Each device has a device type i.e. the VGA and HERC devices both have the device type OUTPUT1.  
Devices with the same device type receive the same message codes and are therefore interchangeable. 
Devices with the same device type may be logically grouped in the device map, so that a message for one device goes to all the devices within the same logical group.  
e.g. 
If there was a need to update a local (PARADOX) database and a remote (ORACLE) database simultaneously, then the DBM logical group would contain PARADOX and ORACLE device names.  When a message was sent to DBM it would be relayed to both PARADOX and ORACLE (the return value from the message would be that returned by the LAST physical device in the logical group).  
INTER-PROCESS MESSAGING 
The message process has responsibility for routing all messages to and from all the devices, this is achieved via the sendmsg() function.  Each device has a physical name and at least one logical group name, messages are sent to logical groups and the message process looks up the logical group in the device mapping and relays the message to each physical device in that group.  The logical groups may change during execution to allow information to be redirected.  
example:
	sending process     message process     devices     sendmsg( screen ,...)   lookup  screen
                 sendmsg( VGA ,...)    VGA device     

Therefore to change from VGA to a new type of screen would only require the new device and a change in the device mapping file.   
The sendmsg function requires at least two parameters, the first is the logical group name and the second is the message code.  If the message code denotes that there should be additional parameters, then these follow.  A typical sendmsg function call looks like this:   
sendmsg( OUTPUT1 ,MESSAGE_O,10,10, The time is %d:%d ,9,30);  
that is, send a message to the OUTPUT1 group (display device) the message code is MESSAGE_O (output). The MESSAGE_O message places data on the device at an x,y co-ordinate (in this case 10,10) the rest of the data takes the same form as the printf() function.  
The original intention was that each device would have an input, output, control and reset (IOC & R) message.  With each of these message types calling a different function within the device. The message would have then been split down into sub-types under those four categories.  
However This has now been changed so that there is only one entry point into each device (the control function) and each message code is considered a sub-type of that function.  The only problem this causes is in the naming of message codes.    
All message codes are defined in types.h,  message codes like MESSAGE_O may be sent to several different device types. While this does not cause a problem, if the name MESSAGE_O was changed for something more reasonable i.e. DISPLAY_DATA, then a new message would need to be defined for each device type that uses MESSAGE_O, all the calling points would need to be changed as well. 
DESIGNER-RUNTIME INTERFACE STRUCTURE 
The data passed between the design tools and the runtime system is in the form of flat files containing either  C  structures or textual information.  These files define the behavior of the system and a broken down into 7 main areas: 
Configuration - various global vars
The configuration file is the starting point for GPA.  It defines all the information regarding paths, filenames, screen savers etc. for the runtime system.  
The configuration file must have the extension  .CFG  and may be passed to the runtime system in one of two ways;  The GPACFG environment variable may bet set to reflect the path and name of the configuration file, or the configuration filename may be passed as argv[1].  
If the configuration file is passed as a command line parameter, the current directory must contain the configuration file and the argument should not contain the .CFG extension. 
e.g.   
C:\STARTUP>  GPA FRED    
NOT  
C:\> GPA \STARTUP\FRED.CFG  

GPACFG should be defined by concatenating the path and the configuration file name 
e.g.   
set GPACFG = \STARTUP\FRED  
Note: If you specify a drive letter it will be ignored.  
The configuration file is a plain ASCII text file with each line containing a keyword followed by some parameter setting(s).  
If a keyword is unrecognized, it is assumed to be a comment and therefore discarded.  There are a number of valid keywords available for use in the a configuration file for a full list please refer to section ????nnn??? in the document ???????????????????.

Forms - G_fid, G_numidx & G_form 
The Forms are stored as 'C' structures in the file accessed via the global variables G_system and G_config the form file name is made up from the path in G_config and a filename made up of the 1-7 letter string in G_system followed by the letter  N  and the extension  .DAT . 
e.g.  if G_config =  CONFDIR\  and G_system =  TESTSYS . Then the file containing the form information is named   CONFDIR\TESTSYSN.DAT .  
The file contains the form structures as outlined below :  
There are two structures associated with forms. These are FORM and FORMF (defined in types.h):  
FORM structure 
Each form is defined by a FORM structure giving it s name, the number of formfields on the form (numitem), the user access level required to process the form, the top/left and bottom/right co-ordinates of the form (bounds), the form type, the form attributes(attribs), the current formfield being processed (curitem) and a pointer to a list of FORMF structures (items) that refer to the formfields.    
typedef struct {		// Form Structure    
	CHAR	name[9];	// form name    
	UCHAR	numitem;	// the number of items    
	INT16	access;	// form access level    
	WIN	bounds;	// form boundaries    
	INT16	type;		// form type    
	CHAR	attribs;	// form attributes     
	INT16	curitem;	// the current item     
	FORMF	*items;	// the list of items    
} FORM;  
name		must be no longer than 8 characters and the terminating NULL. 
numitem	must reflect the length of the array pointed to by items. 
access		is set to Zero by default (any user may process) and may contain any value between 0-9.
bounds	is Currently unused. 
type		may be one of six values (defined in formhand.h):      
		F_NORM - a plain screen form      
		F_SERVE - a screen form used for point of sale      
		F_PROMPT - a screen form for use on small VDU s      
		F_MENU - a screen menu      
		F_REPORT - a plain paper report      
		F_PPFORM - a report for output on pre-printed stationary 
attribs		is Currently unused. 
curitem	is only valid during form processing and reflects the offset in the items array of the current 
		formfield being processed. When valid, it contains a number between -1 and numitem+1. 
items		must point to a valid address containing numitem FORMF structures.   


FORMF structure 
Each formfield is defined by a FORMF structure giving it s name, form field type, a unique identifier (ident) (unique within a form), an x,y co-ordinate (pos) in character offset from top/left origin, the formfield colour attributes (attrib), The formfield font size, The formfield classification (class), The action associated with a formfield (func), the input or output data (item), and the input picture format (fmt).     
typedef struct {		// Form Field Structure
	CHAR	name[9];	// field name
	CHAR	type[9];	// field type
	UCHAR	ident;	// unique field identifier
	XYPNT	pos;		// x/y co-ordinates
	CHAR	attrib;	// field attributes
	UCHAR	size;		// field size
	INT16	class;	// item classification
	CHAR	func[9];	// validation function
	CHAR	item[60];	// item
	CHAR	fmt[40];	// input format
} FORMF;
name		must be no longer than 8 characters and the terminating NULL. 
type		must be no longer than 8 characters and the terminating NULL.This element is no longer used to hold type information and is instead used to hole the VARIABLE name associated with the form field. (the name  type  was never changed!) 
ident		is set to a value within the form designer and is used to reference a formfield.
pos		is a positive offset. attrib  if MSN >0 background colour=palette[MSN] otherwise foreground      colour=palette[LSN]. size   0=single height & width, 1=single height double width, 2=double height & width. 
class		may be one of ten values (defined in formhand.h):
		FF_MAND - the field requires mandatory input
		FF_OPTI  - the field is optional
		FF_SRCH - the field contains the information required by            a primary search.
		FF_TEXT - the field is a text output field
		FF_MSRH - combination of FF_MAND and FF_SRCH
		FF_MSEC - combination of FF_MAND and FF_SECS
		FF_WAIT - this field is display only but requires a key press for the form processing to proceed.      
		FF_DISP  - a display data only field      
		FF_SECS - the field contains the information required by a secondary search.      
		FF_TABL - this field is the outline of a table containing the references to all of the fields within the table.     Each of the above will be OR ed with FF_TBLF if the field referred to is contained within a table. 
func		this may contain  "", "NONE", "NONE    " or a valid action name 
item		this may contain one of three possible types of information depending on the formfield class.  If the class is FF_TEXT then this will contain the text reference name.  If class is FF_TABL then this will contain the unique identifiers of the fields contained in the table. If class is NOT FF_TEXT OR FF_TABL then this may contain a reference to a datastore field in the format table.field. 
fmt		If class is FF_TABL then this will contain a formatted string of bytes defining the border style and column lengths of the table. If not it will contain the input/output picture  for the field i.e.  XX-999.AA.
